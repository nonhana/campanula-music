## 低视力检查的方法

- 320 CSS px 是竖向内容在窄视口下的重排检查；它对应从 1280 CSS px 放大到 400% 时的可用宽度，不冒充操作系统真的执行了缩放。
- 文字间距使用行高 1.5、段后间距 2em、字距 .12em、词距 .16em，检查必要操作的标签和功能没有丢失。
- 200% 文字模拟先读取文字端点的原字体和行高，再同时翻倍；每个新状态重新移除旧覆盖后采样，避免重复放大。项目字体是 px，单改 html 的 font-size 不能证明文字真的变大。这项模拟不等于系统浏览器缩放的完整验收。
- 强制颜色用 Chromium `forcedColors: active`。文字/选中/焦点和自绘控件需有可辨认的绘制，不能只以 axe 没报错当作通过。系统高对比度主题的最终效果仍需作者试用。

新增检查复现并修复了短信标签/验证码按钮的固定尺寸挤字、歌曲与队列的固定行高重叠，以及强制颜色下渐变滑轨消失、选中状态只靠背景色的问题。文字模拟回归会检查实际文字范围，轨道像素检查用已知完整、缺失和低对比度轨道校准，再要求真实控件达到 3:1 的绘制覆盖；不能以不可靠的伪元素计算样式代替实际绘制。

数值依据：[W3C Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)、[Resize Text](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html)、[Text Spacing](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html)。

## axe 的独立复核

原有 342 条文字对比度观测及其映射保持，继续由 27 组数值回归核验，不改门槛，不将 incomplete 冒充 axe passes。

搜索历史采用正确 dialog popup 后，axe-core 4.14 的 aria-controls 预检查会对显式 aria-haspopup 给出 `controlsWithinPopup` 的 incomplete，即使目标确实存在且角色正确。只登记 desktop / search-history / aria-valid-attr-value / `.bg-transparent` 这一节点，并保留原始结果。搜索回归独立验证目标存在且有名称、role 为 dialog、展开时可见、输入框控制关系和键盘进入/离开；这项没有留待作者判断，也没有对整个规则放行。弹层语义依据 [W3C Combobox Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/)，模态循环依据 [Modal Dialog Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)。

同形检查还覆盖歌单导航/排序行、下载任务失败后的重试按钮。Alt 方向键换序后等待 DOM 更新，再把焦点归还给原触发控件并允许浏览器滚入视口；刷新确认远端顺序。队列增大或恢复文字时允许浏览器原生滚动锚定，但不得重新执行打开时的定位而跳回当前歌曲。测试环境的 Mock 标记不属于产品文字，200% 模拟不放大这枚诊断标记；完整 axe 仍保留它。

## 作者试用

以下项目不由本轮自动化证明，部署后可按这些步骤查看：

1. 用真实读屏打开桌面搜索框，搜一次后清空。应能听到历史弹层和词条；方向键先进入历史词，Tab 能走到清空/离开，Escape 收起并回到输入框。失败表现是只听见“已展开”却找不到历史，或焦点消失。搜索只改本机历史，可用清空撤销。
2. 开始播放并打开播放页，用 Tab / Shift+Tab 走过首尾；手机打开播放队列后再试。焦点应始终在最上层，Escape 先关队列、再关播放页，并回到原入口。用 TalkBack 查看时应能区分当前层和其下不可操作内容。
3. 在桌面 Chrome/Edge 用浏览器菜单放大到 200%，再到 400%；查看短信登录、歌单、编辑弹窗和播放页。主要操作仍应可见可达，竖向内容不应要求左右来回滚。放大后按浏览器菜单恢复 100%。编辑仅使用临时歌单，试完改回原名或删除。
4. 开启系统高对比度模式，查看登录方式、标签选择、焦点、进度和音量。选中状态应能在焦点移走后辨认，轨道与滑块不应消失；完成后恢复原系统设置。
5. 系统开启“减少动态效果”后重复开关播放页和队列，焦点顺序与关闭归还应相同。Android 系统返回应先关顶层，再回页面。
